
# 写日志

> **格式的机械定义在 `日志\build-index.mjs`** —— 它是执行者，跑一遍就知道对不对，不用在这里抄一遍正则。

## 0. 一分钟版

1. 打开/新建 `日志\YYYY-MM-DD.md`（**文件名必须是这个格式**，别的名字整个文件不进索引），第一行写 `# YYYY-MM-DD`。
2. **先定档再动笔**：A ≤600 字符 / B 601–1500 / C >1500，缺省 B。见 §2.3。
3. 每条写成三行：`N. **标题**` / 空行 / `W 空格 + 正文：…`（`W` = 编号位数 + 2），之后才是 `-` 子项。编号当天从 1 连续往下排。见 §2.1。
4. 正文四条硬要求（§2.4）：给具体标识符、给证据、写否定面（四类占一即可）、引用要能兑现。
5. `node 日志\build-index.mjs` —— 有 FAIL 就修（命令退出码 1）；WARN 看一眼。它会顺手修行尾和 BOM，不用管。
6. `cd 日志; git add -A; git commit -m "docs: YYYY-MM-DD 一句话"`。**`docs:` 前缀不能省** —— 只有改代码才用 `fix:`/`feat:`，日志和文档一律 `docs:`。见 §3。

## 1. 该不该写

**写** —— 命中任一条就写：

1. **新建/删除目录或顶层文档** —— 工作区结构变了
2. **交付成品** —— 做完了东西，别人接手要知道在哪
3. **踩出可复用的坑** —— 下次还会撞上，且不写下来就想不起来
4. **用户改了既定口径** —— 之前是这么定的，现在改成那样

**不写** —— 命中任一条就不写：

1. **单次命令的中间产物** —— `npm install` 的进度、临时文件的路径
2. **纯查询** —— 问了什么答了什么，没有产生任何持久改变
3. **别处已有归宿的内容** —— 细节写在某份文档里了，日志压成一行指针
4. **会变的数字写成结论** —— 行数、份数、字节数当天就可能失真。

拿不准就问用户一句。日常小事不问也不写。

## 2. 怎么写

### 2.1 骨架

````markdown
# 2026-10-19

1. **取消封卷机制**

   正文：理由是 5 条易错点里 4 条来自剪切动作本身。

   - 实测：旧日志 196 条，`^\d+\.\s+\*\*` 只匹配到 180 条
   - **不加粗等于索引里查不到** —— 硬要求，不是偏好

2. **索引生成器跑通**

   正文：188 条 → 5,528 字符，占 100 万窗口的 0.3%。
````

**六种行，没有第七种。** 归不进下面任何一类的行，生成器一律 FAIL「未归类行」：

| 行类型 | 写法 | 数量 |
|---|---|---|
| 日期标题 | `# YYYY-MM-DD` | 每文件恰好 1 个，第 1 行 |
| 空行 | 长度 0（不含任何空格） | 只在 5 个位置，每处恰好 1 个 |
| 条目 | `N. [字段…] **标题**` | 每条恰好 1 个，顶层无缩进 |
| 正文段 | `W` 空格 + `正文：…` | 每条恰好 1 个 |
| 子项 | `W` 空格 + `- 内容` | 0 个到任意多个 |
| 围栏 | `W+2` 空格的 ` ``` ` 块 | 只能嵌在子项里 |

**`W` = 编号位数 + 2**：`1. ` 是 3 空格，`10. ` 是 4 空格，`100. ` 是 5 空格。这不是美观问题 —— 缩进少一格，Markdown 就从这里断开列表，后面所有子项掉出条目，读的人看到的是一个碎掉的列表。

**空行只允许在这 5 处**，每处**恰好 1 个**：日期标题后、条目行后、正文段后接子项、正文段后接下一条（本条无子项）、最后一个子项后接下一条。不许连续两个空行，不许文件首尾有空行，空行里不许有空格。围栏内部是例外，原样保留。

「只允许」和「必须有」是两件事，两个都查：这 5 处**少了空行**一样 FAIL。少了它 Markdown 会把下一行并进上一块 —— 条目行紧接正文段时，正文就和标题挤进同一个文本块，「正文段」这个结构当场失效，等于没解耦。

**正文段为什么要另起一行。** 写在标题行 ` —— ` 后面的话，索引取不到（索引只取两个 `**` 之间）；而且「这条叫什么」和「这条讲了什么」挤在同一行，改标题就得动正文。`正文：` 前缀是给机器认的锚点，**不能省**。

**方括号字段是预留位**：`N. [time=14:32:05][tier=B] **标题**`。只认 `[小写键=值]`，0 个或多个都行，当前不强制任何字段 —— 加时间戳、加档位标签都在这一处，不用再改格式。

### 2.2 标题

**判据：单独抄进索引，三个月后还认得出指的是什么。**

长度不是判据。`[2] 待办`、`[4] ★ 自评` 这种抄进索引等于没写；80 字的长标题只要讲清了也行。

### 2.3 三档详略

动笔前先定这一条按哪一档写，并**说出口**（「这条我按 A 记」）。没说就是 B —— 档位是写之前定下的承诺，不是写完之后量出来的标签。

长度按**整条字符数**算（含标题行，不含条目之间空行）。

| 档 | 长度 | 典型 |
|---|---|---|
| **A** | ≤ 600 | 新增了一个目录、改了一个默认值 |
| **B** | 601–1500 | 换了条路线，以及为什么不走另一条 |
| **C** | > 1500 | 一次调查的完整链路 |

**怎么定**：用户说了「简单记 / 详细记」就按他说的；没说，按「这条将来会被谁、在什么场合再读一次」判断 —— 只有自己回头瞥一眼 → A；要拿它做决定 → B；别人（或三个月后的自己）要照着复现 → C。

**档位只限制篇幅，不规定写什么。** 装什么内容由 §2.4 统一管，三档都一样 —— 档位砍的是篇幅，不是密度。A 档写成「优化了配置」不算达标；写成「把 `~\.gitconfig` 的 `autocrlf` 删了」才是 A 档。实测也印证了：A 档 46 条里 40 条（86.7%）确实写全了具体化 + 证据 + 否定面，**短不等于缺内容**。

**C 档必须有一句写明细节在哪份文档**；实在没有别处，就写明「这段本身就是归宿」。C 档是「允许写长的唯一条件是有出路」，不是「允许写长」。

**升档要理由，降档不要。** 想用 C 档，得说清为什么这段不能被压掉。反过来，能压到 A 不必解释。

**档位不是质量分级，别为了升档灌水。** A 档既最容易写成空壳，也最容易被几个月后的人回头引用 —— 全库被独立引用最勤的一条只有 130 字符。

**档位不是分类标准。** 一件事该不该拆成两条，看的是「标题能不能各自成立」，不是长度。业务交付和技术排查混在一条里，才会出现「标题叫 A、内容全是 B」，将来按 B 去翻永远翻不到。

### 2.4 正文四条硬要求

| 要求 | 反例 | 正例 |
|---|---|---|
| **具体化** —— 给标识符、路径、命令、数字 | 改了相关配置文件 | 改 `~\.gitconfig` 第 3 行，删掉 `autocrlf` |
| **给证据** —— 凭什么这么说，说清楚 | 应该是缓存问题 | 实测：清空 `session_projcache` 后症状消失 |
| **写否定面** —— 四类，占一即可（见下） | 修好了 | 不是权限问题（换管理员跑仍失败），是路径用了中文名 |
| **引用兑现** —— 指向的条目/章节真的存在（见下） | 见第 8 条之后的修订记录 | 见 §2.5 的 FAIL 表 |

**否定面的四类** —— 一条里写出一类就算达标，不必四类齐全：

1. **不是这个原因** —— 排除了什么错判。`不是权限问题：换管理员跑仍失败`
2. **这个没做 / 没验证** —— 划出可信边界。`declined 拒绝分支从未在真实宿主跑过`
3. **别这么做** —— 留个坑给下一个人。`别用 Set-Content 改日志，会造 \r\r\n`
4. **我原以为 X，实际是 Y** —— 把被推翻的那个判断写出来。`原以为是缓存问题，实际是路径里有中文名`

第 4 类最容易漏：只写 Y 不写 X，三个月后没人知道这条结论在反对什么。

**只对真实存在的怀疑写否定面。** 给一个物理上不可能的怀疑打补丁，等于把这条当填空题做 —— 比如为「tgz 会不会被引用检查漏掉」写否定面，而那个脚本根本不扫 tgz。

不设强制字段（`现象：`/`根因：`/`修复：`）。那种模板对「用户改了既定口径」「第 5 条验收通过」填不进去，**填不满就会诱导编造**。

**推荐 `-` 拆点**：一条讲 3 件事写 3 个 `-`，比一大段好扫。

**引用要能兑现。** 写「见第 N 条」「§X」「某份文档的某节」之前，先确认它真的存在 —— 悬空的锚点会一直安静地骗人。日志里已有实例：一条正文写着「见第 8 条之后的修订记录」，而那一节从来没存在过，过了 4 天没人发现，还让一条空正文条目被错记成「被引用过」。本条从写下之日起适用，历史条目按 §2.6 不回头改。

### 2.5 生成器会拒绝什么

**FAIL —— 必须修**（命令退出码 1）。这一组全是「你以为记了，其实没进索引」：

> **下面这些里有一批生成器会先自己修掉。** 缩进不对、空行位置／数量不对、空行里带空格、行尾不对、BOM —— 这几类答案是唯一的、只动空白，默认入口直接修好并单列一段「已自动修复 N 处」。其余（标题为空、正文还在标题行上、两个正文段、未归类行…）答案不唯一或要改字，脚本不动，必须你自己改。

| 错法 | 后果 | 正确 |
|---|---|---|
| 文件名不是 `YYYY-MM-DD.md`（如 `2026-10-22-补充.md`） | **整份日志被跳过**，一条都不进索引 | 一天一个文件，补充内容就接着往下编号 |
| 文件名里的日期不存在（如 `2026-02-30.md`） | 整份不会被收录 | 用真实存在的日期 |
| 第一行不是 `# YYYY-MM-DD` 日期标题 | 认不出这是哪天的日志 | 第一行就写日期标题 |
| 日期标题与文件名不一致 | 索引和文件名对不上 | 两处写同一天 |
| **文件中间又出现一个日期标题** | 它既不生效、也不报错，索引里那些条目还全被记在前一天的日期下 —— 日期标题成了纯装饰物 | 每个文件只有一个日期标题，就是第一行 |
| 空文件 | 没有内容可收 | 没东西要记就别建文件 |
| 文件读不出来（是个目录／没权限） | 整份跳过 | 检查路径与权限 |
| **未归类行** —— 归不进那六类的任何一行 | **每一行都必须有定义**，没定义的行说明写法是临时起意的 | 按 §2.1 的六类写 |
| 条目行**标题是空的**（`1. **   **`，只有空白） | 索引里会出现一条没有标题的条目 | 两个 `**` 之间写真正的内容 |
| 条目行**标题后面还有内容**（`1. **标题** 多余的话`） | 标题行只能装标题，索引也只取标题 | 多余的话进正文段或子项 |
| 正文**还写在标题行上**（旧的 ` —— ` 写法） | 索引取不到那段话，而且改标题会牵动正文 | 另起一行，`W` 空格 + `正文：…` |
| 某条**没有正文段**，或只有一个空 `正文：` | 这条只剩个标题，等于没讲发生了什么 | 每条恰好一个非空正文段 |
| 一条里有**两个正文段**，或**子项先于正文段** | 结构歧义：到底哪句是正文 | 正文段紧跟条目行，之后才是子项 |
| 正文段／子项**缩进不对**（不是 `W` = 编号位数 + 2） | Markdown 从这里断开列表，后面子项全掉出条目 | `1. ` 用 3 空格，`10. ` 用 4 空格 |
| 围栏**缩进不是 `W+2`**，或围栏不在任何条目内 | 围栏失效，代码被当正文渲染 | 围栏嵌在子项里，再缩进 2 格 |
| 空行**位置不对**、**连续两个**、**文件首尾有空行**、**空行里带空格** | 渲染出段间大缝隙或列表断裂 | 只在 §2.1 那 5 处各留 1 个真空行 |
| **该有空行的地方没写**（条目行紧接正文段、正文段紧接子项…） | 少了它 Markdown 把下一行并进上一块，正文段这个结构当场失效，而生成器一声不响 | 那 5 处不是「有空行才合法」，是「必须有空行」 |
| `1. 学说系统：…` **不加粗** | 索引里查不到，**AI 永远找不到这条** | `1. **学说系统换代**` |
| 正文里写 `    1. **子项**`（缩进 + 加粗） | **整条静默消失**：不报错、不进索引，你以为记下了其实没有 | 缩进子项**不要加粗**，用 `-` 代替 |
| 编号写成全角 `１.`、顿号 `1、`、或缺空格 `1.**标题**` | **完全静默**：退出码 0、索引 0 条、零提示 —— 最坏形态，看着像记了 | 半角数字 + 半角小数点 + 一个空格 |
| 方括号字段不合法（`[TODO]` 缺等号、键含大写） | 那个字段被当成标题的一部分，或整行认不出 | `[小写键=值]`，如 `[time=14:32:05]` |
| 修复结果写不回文件（被占用／只读） | 索引按内存内容生成不受影响，但磁盘上那个文件还是坏的 | 处理掉占用或只读，重跑一次 |

**WARN —— 看一眼**（不阻断，确认不是真出了问题）：

| 错法 | 后果 | 正确 |
|---|---|---|
| 编号跳号（7 → 9） | 看着像丢了一条 | 要么补上，要么让编号连续 |
| 编号重复（1、1、2）或倒序（2、1） | 顺序错乱，条目引用会指错 | 按 1、2、3 往下排 |
| 出现「概览」行 | 该机制已取消，它不进索引，等于白写 | 别写，按天分文件后扫标题就够了 |
| 代码围栏没闭合 | 往后的条目全被当成代码，一条都收不进来 | 围栏记得闭合 |
| 含无法解码的字节（疑似非 UTF-8） | 索引里是乱码，且生成器查不出来也修不了 | 用编辑器另存成 UTF-8 |
| 祖先目录里也有 `日志\`（只在你把脚本放在工作区根时提示） | 可能把脚本复制错了位置，索引写到了子工作区 | 确认 `build-index.mjs` 是放在 `<工作区>\日志\` 还是 `<工作区>\`，只留一份 |

**代码围栏是安全区。** ```` ``` ```` 或 `~~~` 包起来的内容（比如贴一段格式示例）不参与任何判定，不会被当成条目收进索引，也不会误报 FAIL。

### 2.6 两条纪律

1. **写完不回头改。** 说错了就补一条新的（`3. **更正第 1 条**`），不改旧条目。日志记的是"当时怎么想的"。
   - 也**不许在旧条目里插注解**（"后来它于 X 日迁走了"）。这与"改旧条目"直觉上不同 —— 前者像篡改，后者像补充 —— 但结果一样：把当前状态混进历史，以后读那天的人会以为当时就知道结局。想记后续，就新开一条。
2. **不记写入时间戳。** 条目的先后顺序本身就是时间序。时间只在**它是内容的一部分**时才写（「（22:41–23:03）」说明这件事花了 22 分钟，这是事实）。

### 2.7 落盘的两个坑

**行尾统一 CRLF。** 写文件的工具默认输出 LF，光靠约定守不住，所以生成器默认模式会把日志文件的行尾修正成 CRLF —— 它跑的时候日志一定已经写完了，是天然的检查点。报告里有「行尾修正为 CRLF：xxx」就说明刚修过，不用管。`.gitattributes` 里另有一份声明（`*.md text eol=crlf`），那是给 git 看的，管不到工作区里已存在的文件。

> **PowerShell 会制造 `\r\r\n`。** 用 `Set-Content`/`Add-Content`/`Out-File` 写**已含 CRLF 的字符串**时，它按 `\n` 分行再以 `\r\n` 连接，于是每个换行前的 `\r` 都被留下，变成 `\r\r\n`。这种文件 git 会判定成二进制（`git ls-files --eol` 显示 `i/-text w/-text`），diff 里什么都看不见。生成器的收敛逻辑能修掉它（报告里会写「行尾修正为 CRLF」），但**别用这几个 cmdlet 改日志**——用 `[System.IO.File]::WriteAllText($abs, $text, [System.Text.UTF8Encoding]::new($false))`，且必须传**绝对路径**（`cd` 只改 PowerShell 位置，.NET 静态方法用的是进程工作目录）。

**BOM 与编码。** 某些编辑器 / PowerShell 5 的 `Out-File` 会给文件加 UTF-8 BOM，那会让第一行认不出日期标题。生成器默认模式会自动剥掉并写回（报告里写「剥离 UTF-8 BOM」）。反过来，**非 UTF-8 编码（如 GBK）查不出来也修不了** —— 只会报 WARN「疑似非 UTF-8」，索引里还是乱码，得自己用编辑器另存成 UTF-8。

## 3. 写完做什么

```powershell
cd D:\AI\deepseek2
node 日志\build-index.mjs        # 先修能修的，再报修不了的
cd 日志
git add -A
git commit -m "docs: YYYY-MM-DD 一句话"
```

**它会先修，再报。** 生成器默认会尝试修掉「答案唯一、只动空白」的那几类错（缩进、空行位置与首尾多余空行、空行里的空格、行尾、BOM），报告里单列一段：

```
已自动修复 3 处（只动空白与空行，一个字没改）
  2026-10-25.md: 第 17 行 正文段缩进 3 → 4 空格
  2026-10-25.md: 补上 2 个缺失的空行
```

看到这一段，**提交前先核一遍它说的是不是真的**：

```powershell
git diff -w --ignore-blank-lines -- 日志\
```

只改了缩进和空行时它输出为空；只要有一个字被改动，它会立刻显示出来。核完再 `git add`。

**修不了的照旧报 FAIL**，比如「正文还写在标题行上」「第二个正文段」—— 那些要人决定怎么改，脚本不动。想只看校验结果、不落盘任何修复，加 `--no-fix`；只想看每行归哪一类，加 `--explain`。

**commit 标题必须带前缀**（Conventional Commits）：只动日志/文档用 `docs:`，改代码用 `fix:`／`feat:`／`refactor:`，改插件版本用 `chore:`。前缀让「这次提交到底动了什么」在不点开 diff 的时候就成立。

只有 FAIL 会让命令以退出码 1 结束；**WARN 不阻断**。两类各是什么、怎么改，见 §2.5。

**索引是先生成、后判 FAIL 的** —— 所以即使在 FAIL 的情形下，磁盘上的 `_日志索引.md` 也已经写出来了（少了出错的那条）。看到 FAIL 就修完重跑，不要以为「报错了所以索引没动」。

**别的文档要指某条日志，用「第 N 条」，不要用行号。** 索引给的就是这个形态：

```
- 10-25  补上三条缺失类检查 · 日志\2026-10-25.md 第 4 条
```

引用时最好再带一句标题（`` `日志\2026-10-25.md` 第 4 条「补上三条缺失类检查」 ``），`tools\check-refs.mjs` 会核对「第 4 条」现在的标题还是不是那一句。行号锚点（`日志\2026-10-25.md:88`）插一个空行就整体漂，而它漂的时候不报错 —— 只是安静地指向别的条目。条目编号只在拆条/合并、或改写标题时才失效，那本来就是该被看见的变化。

**生成器全绿不等于日志合格。** 机器查不了的只能靠自己：正文的具体化／给证据／写否定面（§2.4）、引用是否兑现（§2.4）、标题判据（§2.2）、写完不回头改与不记时间戳（§2.6）、该不该写（§1）。

## 4. 已取消的机制（别复活它们）

| 机制 | 为什么取消 |
|---|---|
| 封卷 | 5 条易错点里 4 条来自剪切动作本身；它能做的事已被"按天分文件"免费做到 |
| 衔接区 | 它把"同一天三份副本"造出来，还要求肉眼核"一字不差" |
| 按月分卷 | 卷文件长到 73 KB，只能靠行号定位 |
| 待办标记与汇总 | 实测旧系统 8 条待办里 3 条早做完了，是上磁盘查出来的，不是日志标的。做出来是一堆显示着已完成事项的噪音 |
| 写前过目的人工确认 | 记忆的价值来自量大、低摩擦；确认门槛会把记忆退化成文档编辑 |

根子是同一个：**它们都是"派生数据"被当成"真源"在维护。**

**「被谁引用」也是这一类。** 入链在写这一条的时候还不存在，要让它出现在文件里，就得回头改旧条目 —— 与 §2.6「不回头改」直接冲突。文件里只写出链（这条引用了谁），入链靠扫全库算出来。
