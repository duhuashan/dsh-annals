
# 写日志

> **格式的机械定义在 `日志\build-index.mjs`** —— 它是执行者，跑一遍就知道对不对，不用在这里抄一遍正则。

## 0. 一分钟版

1. 打开/新建 `日志\YYYY-MM-DD.md`（**文件名必须是这个格式**，别的名字整个文件不进索引），第一行写 `# YYYY-MM-DD`。
2. 每条写成 `N. **标题** —— 正文`，编号当天从 1 连续往下排。缩进子项用 `-`，**不要加粗**。
3. 正文给具体标识符、给证据、写否定面。
4. `node 日志\build-index.mjs` —— 有 FAIL 就修（命令退出码 1）；WARN 看一眼。**它顺手把行尾修正成 CRLF、剥掉 UTF-8 BOM**，不用管。
5. `cd 日志; git add -A; git commit -m "..."`。

## 1. 该不该写

### 写（正向清单）

命中任一条就写：

1. **新建/删除目录或顶层文档** —— 工作区结构变了
2. **交付成品** —— 做完了东西，别人接手要知道在哪
3. **踩出可复用的坑** —— 下次还会撞上，且不写下来就想不起来
4. **用户改了既定口径** —— 之前是这么定的，现在改成那样

### 不写（反向清单）

1. **单次命令的中间产物** —— `npm install` 的进度、临时文件的路径
2. **纯查询** —— 问了什么答了什么，没有产生任何持久改变
3. **别处已有归宿的内容** —— 细节写在某份文档里了，日志压成一行指针
4. **会变的数字写成结论** —— 行数、份数、字节数当天就可能失真。

### 不确定时

拿不准就问用户一句。日常小事不问也不写。

## 2. 怎么写

### 2.1 骨架

```markdown
# 2026-10-19

1. **取消封卷机制** —— 理由是 5 条易错点里 4 条来自剪切动作本身。

2. **索引生成器跑通** —— 188 条 → 5,528 字符，占 100 万窗口的 0.3%。
   - 实测：旧日志 196 条，`^\d+\.\s+\*\*` 只匹配到 180 条
   - **不加粗等于索引里查不到** —— 硬要求，不是偏好
```

### 2.2 八个易错点

| 错法 | 后果 | 生成器 | 正确 |
|---|---|---|---|
| `1. 学说系统：…` **不加粗** | 索引里查不到，**AI 永远找不到这条** | FAIL | `1. **学说系统换代** —— …` |
| 正文里写 `    1. **子项**`（缩进 + 加粗） | **整条静默消失**：不报错、不进索引，你以为记下了其实没有 | FAIL | 缩进子项**不要加粗**，用 `-` 代替 |
| 编号跳号（7 → 9） | 看着像丢了一条 | WARN | 要么补上，要么让编号连续 |
| 编号重复（1、1、2）或倒序（2、1） | 顺序错乱，条目引用会指错 | WARN | 按 1、2、3 往下排 |
| 条目之间**不空行** | Markdown 渲染时两条并成一段，人读是糊的 | WARN | 每条后面空一行 —— 松散列表，见 §2.1 骨架 |
| 文件名不是 `YYYY-MM-DD.md`（如 `2026-10-22-补充.md`） | **整份日志被跳过**，一条都不进索引 | FAIL | 一天一个文件，补充内容就接着往下编号 |
| 编号写成全角 `１.`、顿号 `1、`、或缺空格 `1.**标题**` | **完全静默**：退出码 0、索引 0 条、零提示 —— 最坏形态，看着像记了 | FAIL | 半角数字 + 半角小数点 + 一个空格 |
| 标题后**没有正文** | 写日志时断行了，正文被挤丢 | WARN | 标题行后面接着写 ` —— 正文` 或缩进子项 |

**代码围栏是安全区。** ```` ``` ```` 或 `~~~` 包起来的内容（比如贴一段格式示例）不参与任何判定，不会被当成条目收进索引，也不会误报 FAIL。但围栏**记得闭合** —— 没闭合会把后面半个文件全当代码，生成器报 WARN「代码围栏没有闭合」。

### 2.3 标题

**判据：单独抄进索引，三个月后还认得出指的是什么。**

长度不是判据。`[2] 待办`、`[4] ★ 自评` 这种抄进索引等于没写；80 字的长标题只要讲清了也行。

### 2.4 正文三条硬要求

| 要求 | 反例 | 正例 |
|---|---|---|
| **具体化** —— 给标识符、路径、命令、数字 | 改了相关配置文件 | 改 `~\.gitconfig` 第 3 行，删掉 `autocrlf` |
| **给证据** —— 凭什么这么说：实测 / 读代码 / 推测 | 应该是缓存问题 | 实测：清空 `session_projcache` 后症状消失 |
| **写否定面** —— 什么**不**是原因、什么**别**做 | 修好了 | 不是权限问题（换管理员跑仍失败），是路径用了中文名 |

不设强制字段（`现象：`/`根因：`/`修复：`）。那种模板对「用户改了既定口径」「第 5 条验收通过」填不进去，**填不满就会诱导编造**。

**推荐 `-` 拆点**：一条讲 3 件事写 3 个 `-`，比一大段好扫。

### 2.5 两条纪律

1. **写完不回头改。** 说错了就补一条新的（`3. **更正第 1 条** —— …`），不改旧条目。日志记的是"当时怎么想的"。
   - 也**不许在旧条目里插注解**（"后来它于 X 日迁走了"）。这与"改旧条目"直觉上不同 —— 前者像篡改，后者像补充 —— 但结果一样：把当前状态混进历史，以后读那天的人会以为当时就知道结局。想记后续，就新开一条。
2. **不记写入时间戳。** 条目的先后顺序本身就是时间序。时间只在**它是内容的一部分**时才写（「（22:41–23:03）」说明这件事花了 22 分钟，这是事实）。

## 3. 写完做什么

```powershell
cd D:\AI\deepseek2
node 日志\build-index.mjs        # FAIL 就修，WARN 看一眼
cd 日志
git add -A
git commit -m "YYYY-MM-DD: 一句话"
```

生成器报的错分两类：

| 级别 | 含义 | 处理 |
|---|---|---|
| **FAIL** | 条目未加粗、缩进子项加粗、编号写法不规范（全角数字／顿号／缺空格）、文件名不合规范、文件名里的日期不存在、日期标题与文件名不符、第一行不是日期、空文件、文件读不出来（是个目录／没权限） | **必须修**，否则索引是错的或缺条目 |
| **WARN** | 编号跳号／重复／倒序、标题后没正文、条目间不空行、单日超 20,000 字符、出现「概览」行、代码围栏没闭合、疑似非 UTF-8 编码 | 看一眼，确认不是真出了问题 |

只有 FAIL 会让命令以退出码 1 结束；**WARN 不阻断**。

**索引是先生成、后判 FAIL 的** —— 所以即使在 FAIL 的情形下，磁盘上的 `_日志索引.md` 也已经写出来了（少了出错的那条）。看到 FAIL 就修完重跑，不要以为「报错了所以索引没动」。

**行尾统一 CRLF。** 写文件的工具默认输出 LF，光靠约定守不住，所以生成器每次运行会把日志文件的行尾修正成 CRLF —— 它跑的时候日志一定已经写完了，是天然的检查点。报告里有「行尾修正为 CRLF：xxx」就说明刚修过，不用管。`.gitattributes` 里另有一份声明（`*.md text eol=crlf`），那是给 git 看的，管不到工作区里已存在的文件。

> **PowerShell 会制造 `\r\r\n`。** 用 `Set-Content`/`Add-Content`/`Out-File` 写**已含 CRLF 的字符串**时，它按 `\n` 分行再以 `\r\n` 连接，于是每个换行前的 `\r` 都被留下，变成 `\r\r\n`。这种文件 git 会判定成二进制（`git ls-files --eol` 显示 `i/-text w/-text`），diff 里什么都看不见。生成器的收敛逻辑能修掉它（报告里会写「行尾修正为 CRLF」），但**别用这几个 cmdlet 改日志**——用 `[System.IO.File]::WriteAllText($abs, $text, [System.Text.UTF8Encoding]::new($false))`，且必须传**绝对路径**（`cd` 只改 PowerShell 位置，.NET 静态方法用的是进程工作目录）。

**单日建议不超过 20,000 字符。** 提醒灯不是红线 —— 一天一个文件本身已经限制了最大规模。旧系统定的 5,000 字符线在 2026-10-19 放宽，依据是第一天就写到 4,804 字符：那天是系统上线，密度本来就高，用上线日的密度反推日常线会把线定得比实际需求低四倍。**超了生成器报 WARN**（实测 `2026-10-21.md` 曾到 38,016 字符）。

**不写「概览」行。** 按天分文件后一天通常只有几条，扫标题就够了。写了生成器报 WARN —— 它不会进索引，等于白写。

**有几条规矩机器查不了**，只能靠你自己：正文的具体化／给证据／写否定面（§2.4）、标题判据（§2.3）、写完不回头改（§2.5）、不记时间戳（§2.5）、该不该写（§1）。生成器全绿**不等于**日志合格。

**BOM 与编码。** 某些编辑器 / PowerShell 5 的 `Out-File` 会给文件加 UTF-8 BOM，那会让第一行认不出日期标题。生成器会自动剥掉并写回（报告里写「剥离 UTF-8 BOM」）。反过来，**非 UTF-8 编码（如 GBK）查不出来也修不了** —— 只会报 WARN「疑似非 UTF-8」，索引里还是乱码，得自己用编辑器另存成 UTF-8。

## 4. 已取消的机制（别复活它们）

| 机制 | 为什么取消 |
|---|---|
| 封卷 | 5 条易错点里 4 条来自剪切动作本身；它能做的事已被"按天分文件"免费做到 |
| 衔接区 | 它把"同一天三份副本"造出来，还要求肉眼核"一字不差" |
| 按月分卷 | 卷文件长到 73 KB，只能靠行号定位 |
| 待办标记与汇总 | 实测旧系统 8 条待办里 3 条早做完了，是上磁盘查出来的，不是日志标的。做出来是一堆显示着已完成事项的噪音 |
| 写前过目的人工确认 | 记忆的价值来自量大、低摩擦；确认门槛会把记忆退化成文档编辑 |

根子是同一个：**它们都是"派生数据"被当成"真源"在维护。**
